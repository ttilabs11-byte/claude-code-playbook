# What to take from the tools, methods and harnesses (2026-11-03)

This follows a review that judged 28 popular Claude Code repos yes or no. This document goes one
level deeper. For each idea worth having, it asks how we get its essence at the lowest token cost: a deterministic
script or hook (zero context until it fires), a few lines in an on-demand skill, or one clause in a rules file.
Installs come last.

## 1. The one idea that matters most: runs end, they don't wait

mattpocock's *software-factory* says: "A run never waits for a human: it ends, and the human's later change …
triggers a new run." Every agent factory that scales works this way, with each run's only memory held in
artifacts (tickets, git, logs). That is exactly our biggest cost.

**Our numbers:** 39.5% of all cache writes come from waking a session that sat idle for more than an hour.
**The cost of each path:**
- Waking a 200k-token context rewrites the whole thing at 2×, about 400k token-equivalents.
- A fresh session that reads the stream's session log costs its first prompt, about 30–40k at 2×, roughly 80k.

That makes a fresh start about **5× cheaper** whenever the old context is large and cold.

**Our version (a rule change, so the owner's call):** route by *work stream*, not by *session*.
- A child session finishes, makes sure its session log and handoff are current, and is archived.
- New work for that stream goes to a fresh session that starts from the stream's session log and spec.
  mattpocock's *handoff* rule applies: point to the artifacts, never copy them.
- A cold session gets messaged only when its context is small (under ~100k) or it went idle less than 1 h ago.

**What changes:** the "Orchestrator sessions" rule ("send each task to the session already doing that work")
becomes "to that work stream's newest session; if it's been idle over 1 h with a big context, start fresh from its
log". The lead-guard hook needs no change.

## 3. Methodologies: what each one is, what we already do, what to take

| Method | Core idea | We already | Take |
|---|---|---|---|
| **Spec-driven development**: spec-kit (GitHub, 146k★), OpenSpec (74k★), Kiro (AWS) | The spec is the source of truth and code is generated from it. spec-kit runs constitution → specify → clarify → plan → tasks → analyze → implement. OpenSpec runs propose → apply → archive, with change folders holding *delta* specs that merge into living specs. Kiro writes criteria in EARS form ("WHEN <event> THE SYSTEM SHALL <response>"). | "Specs first" rule (2026-11-02) and `templates/spec.md` with Given/When/Then criteria | §2 #4. **clarify** caps questions at 5 and writes answers into the spec. **checklist** treats requirements like code: is each one testable, quantified, with edge cases defined? **analyze** checks spec, tests and tasks agree. **archive** means a shipped change updates the living spec, which is our "Living documentation" rule made concrete. Skip both CLIs: our one-page spec does the job at a tenth of the ceremony. |
| **Constitution** (spec-kit) | Project principles every spec is checked against | CLAUDE.md is our constitution | Nothing new. |
| **TDD** (superpowers, mattpocock `tdd`) | Red, green, refactor. No production code without a failing test first. | Tests come from spec criteria | For app bugs: write the failing test that reproduces the bug *before* the fix. Our "prove the check can fail" rule already says this; name it in the dev skill. |
| **Systematic debugging** (superpowers) | No fix without root cause. Reproduce, check recent changes, one hypothesis at a time. After 3 failed fixes, question the architecture. | "Check every fact at its source" | Add the 4 phases and "3 failed fixes → stop and rethink" as ~6 lines in the project-scoped dev skill (the app project `.claude/skills`), not in global rules. |
| **Incremental / thin vertical slices** (addyosmani) | Implement, test, verify, commit; under ~100 lines between tests | Step 3, "small, checked steps; pilot one, then roll out" | Nothing new. |
| **Constraint-driven / ratchet** (addyosmani) | The quality bar is a written number that may only move up, enforced by checks | Prose rules only | §2 #3. |
| **Doubt-driven development** (addyosmani) | A fresh-context reviewer, biased to disprove, cross-examines non-trivial decisions | Goldfish subagent (one per big job), self-check pass | Nothing new. Our subagent limit is deliberate, and the goldfish is this pattern at the cheapest dose. |
| **DDD ubiquitous language** (mattpocock) | One shared vocabulary for code, docs and talk | — | §2 #10, per need. |
| **ADRs** (decision records) | One short file per decision: context, decision, consequences | "Decisions" in session logs, RESEARCH.md | For app repos only: `docs/adr/NNNN-title.md` when a decision outlives a session (schema, auth, hosting). Logs scroll away; ADRs don't. |
| **Kanban WIP limits / theory of constraints** | Limit work in progress; fix the bottleneck first | "Fewest sessions", serial finals, subagent cap of 2; cold-wake analysis | Keep. The REVIEW found the bottleneck (cold wakes), and §1 attacks it. |
| **Shape Up** (Basecamp) | Fixed appetite (time budget), variable scope; shape before you build | Premortem, grilling for big jobs | One habit: for big jobs, state an appetite ("this is worth one session / one day"), and cut scope rather than overrun. |
| **Evals-driven** (Anthropic skill-creator, autoresearch) | A skill or prompt change is judged by an eval set, not vibes | `eval/run_eval.py` for wilson-voice | Use it whenever a skill is edited heavily: a small fixed eval set, before and after. |
| **Lean "push right"** (mattpocock loop-me) | Put the human checkpoint as late as possible, with everything prepared, asked once | "Don't stop for approvals I'd obviously give" | Nothing new. Good to know our rule has a name. |
| **Lateral thinking** (de Bono; danium/lateral-thinking) | Provocation, inversion, random stimulus, six hats | — | Per need for strategy work. A 6-line prompt list in your strategy skill beats installing 10 skills. |

## 4. What the big harnesses teach

How big they are (skill, command, agent and hook files, counted 2026-11-03):

| Harness | Files |
|---|---|
| ECC | 1,868 |
| ruflo | 631 |
| wshobson/agents | 500 |
| oh-my-openagent | 244 |
| gstack | 86 |
| BMAD | 40 |
| addyosmani | 36 |
| mattpocock | 42 |
| superpowers | 18 |

**Lessons:**
1. **They all land on the same loop:** understand → spec → plan → small slices → verify with evidence → review →
   retro. Ours has every step. Their size comes from roles, adapters for six tools, and telemetry, not from better
   method.
2. **The good ones move rules from prose into hooks.** gstack's `careful` and `freeze` are hooks.
   planning-with-files has a Stop-hook completion gate. oh-my-openagent's comment-checker is a binary. A hook costs
   no context and can't be forgotten. Our log-guard, lead-guard and shell-guard follow the same idea; §2 #2, #3
   and #9 extend it.
3. **Cheap context tricks worth copying:**
   - mattpocock and gstack mark user-only skills `disable-model-invocation: true`, so their descriptions leave
     every prompt. Our gauntlet-loop already does this; others can follow whenever a skill only ever runs by
     `/name`.
   - gstack's shared preamble ("if it's already in context, don't read it again").
   - BMAD shards big docs, so each step loads only its piece.
4. **Persona swarms didn't win.** BMAD's PM, architect, dev and QA agents, ruflo's swarms and ECC's agent lists
   multiply context for little gain at our scale. One session per work stream plus one goldfish is enough.
5. **Learning systems stay simple at the top.**
   - ECC's "instincts" score confidence on lessons that hooks observe. That is heavy machinery.
   - mattpocock's `retro` sorts each lesson as mechanical (becomes a check) or judgement (becomes a rule).
   - That sorting is the essence, and it costs one clause (§2 #5).
6. **Recovery after compaction is a solved pattern.** planning-with-files re-injects the plan on each turn, and
   oh-my-openagent resets rule caches after compaction. Our session-resume hook already does this.

## 5. Not taken, and why

- **Caveman, ponytail, i-have-adhd:** they cut output, 11% of spend, and break the warm, plain-language rule.
- **claude-mem, mem0, ECC instincts:** they target memory and compaction, about 13% of writes, and session-resume
  covers it.
- **The spec-kit and OpenSpec CLIs:** their process is heavier than our one-page spec. We take their four ideas
  instead (§3).
- **superpowers itself:** its brainstorming makes the human pick an approach before every build. That clashes with
  "decide the direction yourself". We keep its verification and debugging essence (§2 #8, §3).
- **gstack, BMAD, ruflo, ECC, wshobson:** whole harnesses (§4.4).
- **last30days:** our harvest.py and reddit.py research rounds already cover it. Worth one comparison run before a
  round 10.

## 6. Compaction at the right moment (added 2026-11-03)

Question: compact when it pays, not only at the limit? Yes, at two moments, and nowhere else.

- **Before an idle gap goes cold.** Cache writes are 25.9% of spend; cold wakes (a message after more than an hour)
  are 39.5% of writes, about 220k tokens rewritten per wake. Compacting at 55 minutes idle, over 200k, halves that
  rewrite. Cost when nobody comes back (estimate): one summary over a warm cache, about a third of what a returning wake
  saves, so it pays once more than about one in three idle sessions is resumed.
- **At a finished task's boundary.** The next, unrelated task otherwise drags the old one's tool output through every
  call. The model calls `compact_after_turn` when the task is verified and logged and context is over 150k.
- **Not lower than that.** A fresh session starts near 80k and a compacted one sits near 110k, so compacting a
  150k context saves little and costs detail. Mid-task compaction is never worth it.

Built as the `smart-compact` mod (`mods/smart-compact`, 6 tests, two proven to fail on a mutated build). Unverified
until a real session idles 55 minutes: check `~/.claude/logs/smart-compact.log` and the next cache-report.
